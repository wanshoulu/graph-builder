# Intent RSI 有效进化闭环修复设计

日期：2026-10-31  
状态：设计已获方向批准，待规格复核  
目标任务：`fresh-bank-20261016`

## 1. 问题定义

当前系统能够生成和采纳候选，但无法稳定形成真实精度提升。`fresh-bank-20261016` 曾采纳 v3、v4，随后均因复测无法复现而回滚到 v1。根因不是单一模型能力不足，而是四个闭环缺陷叠加：

1. 生产运行使用单票评测，1–2 道边界题翻转即可制造 0.7–1.4pp 的虚假增益。
2. 门禁允许“训练集修复 1 题、完整集不退化”通过，且实现阈值与用户文案不一致。
3. 搜索长期锁定 rank1；模型停止判断早于服务端换阶段，强制探索经常没有执行机会。
4. 旧任务没有独立 test split，采纳前缺少最终确认；前端也没有区分单次分数与稳定分数。

## 2. 修复原则

- 优先消除虚假提升，再提高搜索覆盖率。
- 普通探针保持低成本，只对基线和准采纳候选增加稳定性成本。
- 采纳条件必须由服务端统一计算，前端只展示同一份决策证据。
- 历史单票结果不重写、不伪装成稳定结果。
- 不把重复投票的原始大对象重复写入任务状态，避免 86.6 MB 状态继续线性膨胀。

## 3. 评测分层

### 3.1 三种测量级别

| 级别 | 用途 | 票数 | 可用于采纳 |
|---|---|---:|---|
| `screening` | 反事实探针、早期候选淘汰 | 1 | 否 |
| `stable` | 当前正式基线、进入门禁的候选 | 3，逐题多数票 | 是 |
| `confirmation` | 门禁通过后的独立复测 | 3，重新执行 | 是，且必须通过 |

运行预算按实际票数扣减。开始完整评测前必须一次性预留该测量所需调用数，不能测到一半才因预算耗尽留下不完整证据。

### 3.2 证据模型

完整评测结果增加以下摘要字段：

```text
measurement.mode: screening | stable | confirmation
measurement.repeatVotes: 1 | 3
measurement.completedVotes: number
measurement.confidence: provisional | stable | legacy_single_vote
measurement.baselineKey: string
measurement.caseVotes: 仅保存逐题票数摘要，不嵌入三份完整原始响应
```

原始投票结果继续使用现有内容寻址 artifact 存储；任务状态只保存引用、聚合分数和逐题多数票摘要。

### 3.3 旧任务兼容

- 既有历史结果标记为 `legacy_single_vote`，不修改原分数。
- `fresh-bank-20261016` 下一次运行前先生成 v1 的 stable baseline。
- 旧的 v3、v4 仍显示在历史中，但不能作为稳定精度趋势点。
- 新任务默认创建固定 train/heldout/test 切分；旧任务无 test 时使用 stable + confirmation 双重确认，并明确展示“无独立测试集”。

## 4. 统一采纳门禁

候选只有同时满足以下条件才能进入 `adoptable`：

1. 候选和基线均为同引擎指纹、同数据切分、同口径的 `stable` 测量。
2. 训练集配对比较至少净修复 2 题，且不能只靠分数四舍五入形成提升。
3. 完整集配对净修复至少 2 题。
4. heldout 不得出现净退化；有 test split 时 test 也不得净退化。
5. schema、重复性、生产引擎复核等既有门禁继续通过。
6. 再执行一次 `confirmation`；确认测量仍满足 2–4，才允许采纳。

`1 修 / 0 破` 只能标记为“有希望但证据不足”，不能采纳。`0 修 / 0 破` 必须返回 `no_effect`，不能误报为 `regressed`。

门禁 API 返回结构化原因：阈值、fixed、broken、net、测量级别、确认状态。前端不得自行复刻另一套阈值判断。

## 5. 搜索阶段治理

### 5.1 强制换阶段

- `noImproveRounds` 默认从 3 调整为 2 个“已完成测量但无净增益”的代次。
- 未测量、执行错误和重复候选不消耗无提升额度。
- 换阶段判断必须在模型 `stop`、模型预算停止和 no-leverage 停止之前执行。
- 一旦触发换阶段，至少保留 1 个 generation 给新阶段；没有剩余代数时不得只记录 `forcedStage` 后立刻结束。

### 5.2 最低探索配额

- 每次运行从 stageMetrics 的失败簇生成有序队列。
- rank1 可优先，但同一失败簇连续两代无增益后，必须转到尚未测量的下一簇。
- 对拥有失败样本但 `measuredAttempts=0` 的簇，设置最低 1 个完整实验配额。
- 已被证否的算子进入 dead/降权；已尝试但未测量的算子显示为 attempted，不再显示为 untried。
- 候选计划中的 `expectedGainCases` 只能引用实际 caseId，数量必须和声明一致；不再接受无证据的泛化增益数字。

### 5.3 停止语义

停止原因区分：目标达到、稳定门禁通过、全部有效阶段耗尽、预算不足、用户停止、模型建议停止。模型建议停止不能覆盖服务端尚未执行的强制探索义务。

## 6. 前端呈现

### 6.1 总览

- 主分数显示“当前正式稳定精度”；没有 stable baseline 时显示“待稳定复测”，不把单票分数当正式精度。
- 同时展示目标差距、测量置信度、票数、引擎指纹和最后测量时间。
- 明确显示“当前为何没有升级”：例如“候选仅修复 1 题，低于稳定采纳阈值 2 题”。

### 6.2 正式版本精度趋势

- 右侧新增正式版本趋势图，只以版本事件为横轴。
- stable 正式版本使用实线；历史单票版本使用灰色空心点和虚线，并标注“低置信度历史结果”。
- 采纳、回滚作为事件标记；鼠标悬停显示版本、稳定分数、票数、采纳/回滚原因。
- 候选分数不混入正式版本趋势，另放在实验视图中。

### 6.3 搜索覆盖与决策证据

- 展示各失败簇的失败题数、尝试数、完整测量数、稳定胜出数和当前状态。
- 展示本轮阶段切换时间线，说明为何从 rank1 转向 rank2。
- 候选卡片统一展示 screening、stable、confirmation 三阶段证据，不再只给一个孤立百分比。

## 7. API 与兼容性

- 现有 `repeatVotes` 继续兼容，但内部转换为明确的 measurement policy。
- baseline 端点默认 stable=3；探针默认 screening=1；准采纳评测和确认默认 3。
- 运行摘要和候选详情返回 measurement 元数据、结构化 gate 结果和 stage coverage。
- 旧客户端未传新字段时使用服务端安全默认值，不能回退到单票可采纳。

## 8. 测试策略

### 单元测试

- 多数票逐题聚合、预算预留和中断行为。
- `0 修 / 0 破 -> no_effect`。
- `1 修 / 0 破 -> evidence_insufficient`。
- 训练和完整集均稳定净修复 2 题、heldout/test 不退化时通过。
- 完整集持平、heldout 回退、引擎指纹不一致、确认失败时拒绝。
- 模型建议停止时，服务端仍先执行已触发的换阶段。
- 未测量错误不消耗 no-improvement 额度。

### 集成测试

- 使用会随机翻转单个边界题的 fake scorer，证明单票可能误晋升，而 stable + confirmation 不会。
- 使用确定性增益 fixture，证明真实修复能通过完整闭环并进入可采纳状态。
- 旧任务无 test split 时能迁移并明确降级展示。
- 重复评测只增加 artifact 引用，不把任务状态扩大为三倍。

### 前端与浏览器验证

- 趋势图严格区分正式版本和候选。
- 单票历史点、稳定点、采纳和回滚均可解释。
- 用户能从总览直接理解未升级原因和下一步搜索阶段。

## 9. 不在本次自动执行的动作

- 不自动启动付费模型进化运行。
- 不自动采纳或回滚生产候选。
- 不重写历史分数或删除现有任务证据。

这些动作在代码与确定性测试完成后，由用户单独授权进行生产验证。
